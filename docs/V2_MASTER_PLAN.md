## 1. The problem (six concerns Ian raised)

The current civic blog at `civic-newsletter-build.vercel.app` serves Birmingham. It works end-to-end but has six visible quality problems:

1. **Root URL needs a splash page.** Today the root URL serves Birmingham directly. It should let visitors search for their city, show which cities are live, and capture "request your city" submissions.
2. **City content must move to a subdomain.** Birmingham relocates so the root can become the splash.
3. **Design is lifeless.** Voice is fine; the *visual layout and UX* needs to spark joy. Cards, hierarchy, hero treatment, color, motion.
4. **Content has too much noise.** Example: a published story read "The Birmingham City Council's Budget and Finance Committee is scheduled to meet on April 13, 2026, from 3:30 to 5:00 PM at City Hall, 710 20th Street North, Third Floor. No specific agenda items were listed…" Nothing happened, nothing was decided, no action window for residents — this should never publish.
5. **Headlines are getting truncated.** The current `headline()` web function just slices the first sentence of `summary_text` and adds an ellipsis. We need real headlines generated by Claude.
6. **No source link.** Every story needs a "verify this" link back to its original source.
7. **(Architectural)** Stories read in isolation. A council decision today is disconnected from the budget meeting six months ago and the school board action last month. We need a running-context system.

(That's actually seven, but #1 and #2 are two halves of the same architectural change.)

## 2. Approved decisions (locked in by Ian)

### Hosting and URLs

- Birmingham moves to `birmingham-al-civic-newsletter-build.vercel.app` — a separate Vercel project deploying the same codebase.
- Root `civic-newsletter-build.vercel.app` becomes the splash page (no `CITY_SUBDOMAIN` env var on that project).
- Stay on `.vercel.app` for MVP. Swap to a real umbrella domain (e.g. `civicweekly.com`) before any ad spend.
- Routing is data-driven: the codebase resolves which city to render from the request host + the `cities` table, not from build-time env vars. `web/lib/city.ts` already does this; keep it that way.

### Design

- Voice is fine — visual lift only.
- Two-font system (display + reading), color pulled from each city's `branding_json`, color-coded impact pills, lead-story-larger card hierarchy, hero band per city, character in empty states, skeleton-loaded cards.
- Tailwind utilities only. Don't install a design system. Don't add user accounts or comments.

### Content quality

- New Signal Gate agent (04c) sits between summarizer and verdict. A story must hit at least one of four signals to publish: decision made, action window for residents, material consequence, conflict/disagreement. Zero signals = dropped.
- Crawler / ingestion-QC stage rejects stub-length scrapes (no agenda items, < ~400 chars).
- Headlines: the summarizer prompt already asks Claude for a `headline` field — the insert just throws it away. Capture it on the new `headline` column.

### Source links

- `meetings.source_url` already exists. Web side joins to expose it. Source badge on story cards (compact chip) and on story detail (prominent band at the top).

### Running context

1. **Entity granularity.** One entity per fiscal-year budget cycle (e.g. "FY25 Birmingham Capital Budget"), year encoded in slug. Use `kind = 'money'` for budgets.
2. **Person entities** include public officials AND people present in some official capacity — group liaisons, named-org representatives, club presidents who appear at hearings. Random residents who speak at a hearing do NOT get entity rows.
3. **"Previously..." block goes at the top of the story detail**, above the body and below the source band.
4. **Watching-this-week sidebar** is city-wide for MVP. No tag/category filters yet.
5. **Run a calibration test** of Sonnet vs Haiku for entity extraction before committing to a model. Use ~20 sample stories. Compare entities extracted, false positives, false negatives, cost. Pick the cheapest model that hits quality bar: >90% recall on civic-role persons, >85% recall on places/projects, <10% false-positive rate. Document in `docs/ENTITY_EXTRACTOR_CALIBRATION.md`.

### Operational

- Per `feedback_deploy_to_match_expectations`: commit, push, deploy each phase. Don't describe local-only work as "ready."
- Per `rls_lockdown_required`: every new public table (`city_requests`, `entities`, `story_entities`) ships with RLS + policies from day one.

## 5. Implementation phases

Four phases, each independently shippable. Do them in order. Commit after each step inside a phase.

### Phase A — Signal Gate + Headlines + Agenda Guard

Highest impact on visible quality. The story Ian screenshotted would never have published if this phase had shipped.

#### A.1 Update summarizer to capture headlines

`src/agents/04-summarizer.js`:

- Tighten the headline directive in the system prompt. Replace the line `"headline": "short descriptive headline (max 12 words)"` with stronger guidance: headlines must lead with the decision or action, must be 6–10 words, and must NOT start with "Meeting is", "Committee will", "Council to discuss" — anything that signals non-news. Include 2–3 examples of good vs bad in the prompt:
    - Good: "Council awards $4.2M Avondale water-main contract"
    - Good: "Vote splits 4-3 against new short-term-rental fee"
    - Good: "Public hearing Monday on Five Points rezoning"
    - Bad: "Council holds meeting to discuss water issue"
    - Bad: "Budget and Finance Committee schedules April meeting"
- In the insert mapping (~line 102), add `headline: s.headline || null` to the row. That's it for this agent. Schema column already exists.

#### A.2 Build the Signal Gate agent

Create `src/agents/04c-signal-gate.js`. Skeleton:

- Export `runSignalGate(cityId)`.
- Fetch `qc_status = 'pending'` stories where `signal_score IS NULL` for the city, joined to `meetings` for context.
- For each story, prompt `MODELS.SONNET` via `callClaudeJSON`. System prompt should define each signal precisely:
    - `decision_made`: a vote happened, a contract was awarded, a rule changed, money was committed.
    - `action_window`: public comment open, hearing scheduled with a specific topic, deadline for resident input.
    - `material_consequence`: something will measurably change for residents — service, money, rule, infrastructure.
    - `conflict`: council split, public opposition recorded, alternative proposals discussed.
- Expected JSON output:

    ```json
    {
      "decision_made": { "hit": true, "evidence": "..." },
      "action_window": { "hit": false, "evidence": "..." },
      "material_consequence": { "hit": true, "evidence": "..." },
      "conflict": { "hit": false, "evidence": "..." }
    }
    ```

- `signal_score` = count of hits. `signal_reasons` = array of hit keys.
- Update story with `signal_score`, `signal_reasons`.
- If `signal_score == 0`:
    - Set `qc_status = 'dropped'`.
    - Insert a `qc_log` row with `flagging_agent = 'signal_gate'` and reason describing which signals were checked.
- Optional fast-path: regex-match obvious stub headlines/summaries ("is scheduled to meet", "no specific agenda items were listed") and drop without LLM call.
- Return `{ gated, dropped, errors: [] }`.

#### A.3 Wire Signal Gate into pipeline

`src/pipeline.js`:

- Import `runSignalGate`.
- Insert the call **between summarizer and context-enricher**. Order matters: gate first so we don't pay enrichment cost on stories we're about to drop.
- Log result like other agents.

#### A.4 Crawler / Ingestion QC agenda guard

Prefer modifying `src/agents/02-ingestion-qc.js` (it already scores meetings on length and content match). After the existing scoring:

- If `content_length.word_count < 400` AND meeting type is council/committee AND no agenda items extractable → set `status = 'skipped'` instead of `ingestion_passed`. Log to `qc_log`.
- Lighter alternative: just bump `min_ingestion_score` in `ops_config` so the existing thresholds catch stubs. Try the lighter fix first.

#### A.5 Update web for headlines

`web/lib/supabase.ts`:
- Add `headline: string | null;` to `StoryRow`.

`web/lib/stories.ts`:
- Include `headline` in the `.select()` lists in both `listStories` and `getStoryBySlug`.
- Update the `headline()` helper:

    ```ts
    export function headline(s: StoryRow, max = 110): string {
      if (s.headline) {
        return s.headline.length > max
          ? s.headline.slice(0, max - 1).trimEnd() + '\u2026'
          : s.headline;
      }
      // Legacy fallback for pre-008 stories
      const first = (s.summary_text || '').split(/(?<=[.!?])\s+/)[0] || s.summary_text || '';
      return first.length > max ? first.slice(0, max - 1).trimEnd() + '\u2026' : first;
    }
    ```

#### A.6 Verify and deploy

- `cd web && npm run build` — TypeScript must pass.
- Re-run the pipeline once. Confirm: low-signal stories get dropped; headlines populate.
- Commit each agent change with a clear message.
- Push to GitHub. Redeploy the relevant edge function (see `docs/MVP_STATUS.md` for orchestration — pipeline.js may run as a Supabase Edge Function or a separate orchestrator).
- After the next cron run, query: `select headline, signal_score, signal_reasons, qc_status from stories order by created_at desc limit 10;`. Sanity-check.

#### D.2 Entity Extractor (`04d-entity-extractor.js`) + calibration

Before building production code: **run the calibration test.**

1. Pick 20 representative stories. Birmingham has a small archive — supplement with synthetic stories or a second city if more are needed.
2. Run the extraction prompt twice — once with `MODELS.HAIKU`, once with `MODELS.SONNET`.
3. Compare entities extracted, false positives, false negatives, cost per story.
4. Pick the cheapest model that meets the quality bar: >90% recall on civic-role persons, >85% recall on places/projects, <10% false-positive rate.
5. Document in `docs/ENTITY_EXTRACTOR_CALIBRATION.md`.

Then build `src/agents/04d-entity-extractor.js`:
- Runs after Signal Gate, before Context Enricher.
- Inputs: story summary, headline, transcript span, tags, votes, meeting metadata.
- Prompt rules for `kind = 'person'` (per Ian's decision): include public officials AND people present in some official capacity — group liaisons, named-org representatives, club presidents who appear at hearings. Exclude random residents.
- Match against existing entities for the city: exact `name`/`aliases` first, then trigram or embedding similarity for likely duplicates.
- High-confidence new → insert. Low-confidence → log and skip (no review UI for MVP).
- Insert `story_entities` rows with role + evidence_span.

#### D.3 Context Linker (`04e-context-linker.js`)

- Runs after Entity Extractor.
- For each newly-published story, fetch most recent 5–10 stories per linked entity.
- Prompt `MODELS.SONNET` with today's story summary + the prior stories. Ask for 1–3 sentence "Previously..." paragraph + `referenced_story_ids` array.
- Validation: every referenced ID must be in the supplied input set. Drop the block if not — never display a hallucinated reference.
- Store `previously_text` + `previously_refs` on the story.

#### D.4 Pipeline wiring

`src/pipeline.js`: insert `runEntityExtractor` and `runContextLinker` after Signal Gate.

**Shadow mode for one week.** Extractor + linker write to DB. Web does NOT render `previously_text` yet — gate behind feature flag `NEXT_PUBLIC_SHOW_PREVIOUSLY=false`. Manually eyeball entities + previously_text for quality. After review, flip the flag.

#### D.5 Web — entity pages, "Previously..." block, "Watching this week" sidebar

- New route `web/app/entity/[kind]/[slug]/page.tsx` — renders entity timeline: name, kind, AI description, story count, first/last seen, reverse-chronological story list with role badges, related-entities sidebar.
- `web/app/posts/[slug]/page.tsx` — render `previously_text` block at top (above body, below source band). Inline links to referenced stories. Skip rendering when `previously_text` is null.
- City home sidebar — query top entities by recent (last 30 days) `story_entities` count. Show entity name, most recent date, story count. Click → entity page. Hide section entirely when empty.

For MVP, give dedicated entity pages to `person`, `project`, `policy` only. `place`, `body`, `money` accumulate in DB but no UI yet.
